# チーム共有 Claude Code 運用ガイド

> これはチーム共有の CLAUDE.md テンプレートです。プロジェクトのルートに配置する `CLAUDE.md`、または `~/.claude/CLAUDE.md` にコピーし、既存のルールとマージして使用してください。
> 本ガイドが参照する各論スキル（コーディング規約・テスト・セキュリティ・レビュー・Git）は、`mori-claude-tools` マーケットプレイスの `core-dev` プラグインとして提供されます。

このドキュメントは、標準（バニラ）の Claude Code のみを前提とした共有版の運用ガイドです。委譲方針と各論スキルは `core-dev` プラグインの導入を前提とします。詳細な各論（コーディング規約・テスト・セキュリティ・レビュー・Git）は同梱スキルへ分離しており、必要な場面で自動的に読み込まれます。

---

## オーケストレーション方針（最優先）

### メインセッションの役割

- メインセッションの責務は **オーケストレーション** に集中する: タスク分解・モデル選択・委譲文の作成・進行管理・受入判定（返却証跡の突合）・ユーザーへの報告。
- **実作業はサブエージェントに委譲する**: 実装・修正・テスト作成、調査、計画立案、レビュー・検証は Agent ツールで起動するサブエージェントに任せる。
- **メインは原則 Edit/Write で成果物を作らない**: 軽微な修正でも委譲する。メインが直接書いてよいのは委譲文・todo 等のオーケストレーション用ファイルに限る。
- **受入判定のための読み取り専用操作は例外**: `git status` / `git diff --stat` / `ls` / 生成物先頭数行の Read など、検収に必要な証跡確認はメインが直接行ってよい。
- **詳細は orchestration-core スキル**: タスク分解・モデル選択・委譲文作成・受入判定の前に `core-dev:orchestration-core` スキルを読む。モデル階層と割り当て、委譲の実行規律、エスカレーション、結果の検証の正は同スキル（references/ を含む）である。
- **orchestration-core が未導入の場合**: `core-dev:orchestration-core` スキルが利用できない場合は、作業を始める前に `core-dev` プラグインをインストールする。マーケットプレイスが未登録なら `claude plugin marketplace add TokyoItSchool-dev/claude-common-plugins --scope project` を実行し、続けて `claude plugin install core-dev@mori-claude-tools --scope project` を実行する。インストール後もスキルが読み込まれない場合は、Claude Code の再起動をユーザーに依頼する。

### 並列実行の補足

- **並列とコスト効率**:
  - 並列化は速度のためではなくタスクの独立性のために行う。エージェント1体ごとにコンテキスト読み込みコストが乗るため、数行で済む断片まで別エージェントに割らない（意味のある独立単位が最小粒度）。
  - 各断片には最も安い十分なモデル（多くは Haiku/Sonnet）を割り当てる。
  - 同時並列数はレート制限を圧迫しない範囲に抑える（目安3〜4並列。超える分は順次バッチで処理する）。
- **大量タスクはパイプライン化**: 10件超の同型タスク（大量移行、監査、横断レビュー等）は個別起動ではなく、Workflow ツール等でパイプライン化する。Workflow ツールが利用できない環境では、バッチに分割して Agent の並列起動で代替する。

## 機能実装ワークフロー

1. **調査と再利用（新規実装の前に必須）**: `gh search repos` / `gh search code`（gh CLI が使えない場合は GitHub の Web 検索等で代替）で既存の実装・テンプレート・パターンを先に探す。API の挙動・パッケージの使い方・バージョン固有の詳細は公式ドキュメントや Web 検索で確認する。npm / PyPI / crates.io 等のパッケージレジストリを確認し、実績あるライブラリを優先する。要件を満たすなら実績ある実装の採用・移植を優先する。
2. **計画優先**: 計画ドラフトはサブエージェント（`Plan` / Opus）に委譲。依存関係とリスクを洗い出し、フェーズに分解する。
3. **TDD**: RED → GREEN → IMPROVE。詳細は `core-dev:tdd-testing` スキル。
4. **コードレビュー**: 実装者とは別のエージェントでレビューする。詳細は `core-dev:code-review` スキル。
5. **コミットとプッシュ**: 詳細は `core-dev:git-workflow` スキル。
6. **レビュー前チェック**: CI/CD が通っている・マージ競合が解消済み・対象ブランチに追随済みであることを確認してから依頼する。

## 固有ルール

- **Git 安全規律**: サブエージェントの並列実行中は、`git stash` / `git reset` / `git checkout .` など作業ツリー全体に及ぶ破壊的操作を行わない。進行中の編集が静かに失われる。
- **飾らない文章（mannered prose の禁止）**: 比喩や修辞で直接表現を置き換えない（「ダイヤルを回す価値がある」ではなく「変えてみる価値があるパラメータ」）。文字どおりの表現があるときはそれを使う。ユーザー向け報告・計画書・レビュー所見のすべてに適用し、委譲文の冒頭には次の固定句を含める: `[PLAIN PROSE] Remove all mannered prose: say what you mean; when a literal phrase is available, use it.`
