# UML 正確性レビュー（オンライン書店システム例 8図）

凡例: 【記法】= UML表記の誤り / 【意味】= モデルとしての矛盾 / → 修正内容

## 共通
- 【記法】矢じりがすべて塗りつぶし三角。UMLで塗り三角を使うのはシーケンス図の同期メッセージだけ。遷移・制御フロー・依存・誘導可能性・応答メッセージは開いた矢じり（V字）。
  → 既定を開いた矢じりにし、同期メッセージのみ塗り三角。
- 【記法】ステレオタイプが `<<include>>` と半角不等号。→ ギュメ `«include»` に統一。

## 配置図
- 【記法】ノード内の「ブラウザ」「注文API」等がフォルダ（＝パッケージ記法）。配置されるソフトウェアは成果物（«artifact»）、実行基盤は実行環境（«executionEnvironment»）。
  → «artifact» の矩形＋右上に成果物アイコン。ブラウザは «executionEnvironment»。
- 【記法】通信路の両端の黒丸はUMLに無い記号。
  → 黒丸を削除。
- 【記法】アプリケーションサーバから1本の線が分岐してDBサーバと決済ゲートウェイへ。通信路は2ノード間の関連で、分岐はできない。
  → 独立した2本の通信路に分離。
- 【意味】ノードの種別が不明。→ «device» / «executionEnvironment» を付与。

## コンポーネント図
- 【記法】コンポーネントにフォルダのタブ（パッケージ記法）。→ タブの無い矩形＋コンポーネントアイコン。
- 【記法】提供インターフェース（白丸）が依存の破線の途中に浮いている。白丸は提供側コンポーネントに実線でつなぐ。利用側は白丸へ破線依存、または受け口（ソケット）で接続。
  → 提供側から実線で白丸、利用側から白丸へ破線矢印。在庫・決済はボール＆ソケットの組立コネクタに。
- 【記法】「データアクセス」の黒丸は非標準。→ «use» 依存（破線矢印）に。DBは «database» を付けたコンポーネント。
- 【意味】認証サービスが注文DBを使っていて、注文サービスは注文DBを使っていない。
  → 認証サービス→会員DB、注文サービス→注文DB に修正（通知サービスを右へ移動）。

## ステートマシン図
- 【意味】キャンセル状態から終了状態への遷移が無い。→ 終了状態を追加。
- 【記法】「取消要求（支払い前）」は条件をかっこ書きしている。UMLは `イベント [ガード] / 効果`。
  → 支払い後の取消は `取消要求 / 返金処理`（クラス図の 支払い.返金処理() と対応）。支払い前は `取消要求`。
- 【意味】決済失敗時の振る舞いが無い（アクティビティ図では再選択できる）。
  → 支払い待ちに自己遷移 `決済失敗` を追加。
- 【意味】「支払い済み →(梱包完了)→ 出荷準備中」は、梱包が終わったことで梱包中の状態に入るという逆転した流れになっている。
  → `支払い済み →(出荷指示)→ 出荷準備中 →(出荷 [梱包完了])→ 発送済み`。
- 【記法】状態名が帯の下に置かれ、帯が空。→ 状態名を上部の名前区画に入れ、下の区画に内部振る舞い（entry / do）を記述。

## アクティビティ図
- 【意味】「商品検索」「支払い方法選択」に入力フローが2本直接入っている。UMLではアクションへの複数入力は暗黙の合流（全部そろうまで待つ）になり、ループが永久に始まらない。
  → 直前にマージノード（ひし形）を置き、そこに集めてから1本で入る。
- 【記法】分岐の「はい／いいえ」はガードなので角かっこ。→ `[続ける]` `[終える]` `[成功]` `[失敗]`。
- 【記法】「開始」「終了」の文字ラベルは不要（初期ノード・最終ノードは記号で表す）。→ 削除。

## シーケンス図
- 【記法】Web画面→注文サービスの呼び出しにメッセージ名が無い。→ `注文登録()` と番号付与。
- 【記法】「5 在庫引当」が在庫サービスからの応答（破線）になっている。引当は依頼する操作で、応答ではない。
  → 4 `在庫引当(商品, 数量)`（同期）／5 `引当結果`（応答）。
- 【記法】注文DBからの応答、Web画面→顧客の応答に名前が無い。→ `保存完了`、`完了画面表示` を付与。
- 【意味】顧客は「注文依頼」送信時に活性区間が終わっており、Web画面は同期呼び出し中に非活性になっている。
  → 顧客の活性を注文依頼まで延長、Web画面は注文完了通知を受けるまで活性を継続。
- 【記法】応答メッセージも塗り三角。→ 開いた矢じり＋破線。

## クラス図
- 【記法】関連の途中に塗り三角。これは「関連名の読む向き」記号で、線上ではなく関連名の横に置く。誘導可能性は線端の開いた矢じり。
  → 「所有する ▶」「対象商品 ▶」と名前の横に移動。線端の矢じりは開いた形。
- 【意味】注文と注文明細は全体‐部分（明細は注文と運命を共にする）→ コンポジション（注文側に塗りひし形）。
- 【意味】注文:支払い = 1:1 だと未払いの注文（状態「新規」「支払い待ち」）が存在できない。→ 支払い側を `0..1`。
- 【意味】注文.状態 が String。ステートマシン図の状態と対応させるなら列挙型。→ `状態 : 注文状態`（«enumeration»）。

## ユースケース図
- 【意味】`注文する --«extend»--> 注文履歴確認` は向きも意味も逆。extend は拡張側から基底側へ向け、基底を任意に拡張する場合に使う。注文履歴確認は独立した機能。
  → 注文履歴確認は顧客から直接使う通常のユースケースに。extend の正しい例として `クーポン利用 --«extend»--> 注文する` を追加。
- 【記法】関連線の端の黒丸はUML 2.5では「所有」の意味になる記号。→ 削除。
- 【記法】外部決済サービスがカードのアイコンだけ。外部システムのアクターは棒人間か «actor» の矩形。→ «actor» 矩形。

## パッケージ図
- 【記法】依存矢印が塗り三角。→ 開いた矢じり。
- 【記法】依存の種別が無い。→ 層間依存に «use» を付与（上位層→下位層）。
- 構造（層の並び、アプリケーション層→インフラ層の依存）は妥当。
