# コーディング規約

## イミュータビリティ（重要）

既存オブジェクトを破壊的に変更せず、常に新しいオブジェクトを生成する。副作用を隠さず、デバッグと安全な並行処理を容易にする。

## KISS / DRY / YAGNI

- **KISS**: 実際に動く最もシンプルな解法を選ぶ。早すぎる最適化を避け、賢さより明快さを優先する。
- **DRY**: 繰り返すロジックは共有関数・ユーティリティに抽出する。コピペによる実装のドリフトを避ける。抽象化は重複が現実になってから導入する。
- **YAGNI**: 必要になる前に機能や抽象を作らない。投機的な汎用化を避け、まずシンプルに始めて必要になったらリファクタする。

## ファイル構成

- 「小さいファイル多数 > 巨大ファイル少数」。高凝集・低結合。
- 目安 200〜400行、最大 800行。大きなモジュールからユーティリティを抽出する。
- 種類別ではなく、機能・ドメイン別に構成する。

## エラーハンドリング

- 各層で明示的にエラーを処理する。UI 向けにはユーザーフレンドリーなメッセージ、サーバー側には詳細なコンテキストをログする。
- エラーを黙って握り潰さない。

## 入力バリデーション

- システム境界で必ず検証する。処理前に全ユーザー入力を検証し、可能ならスキーマベースの検証を使う。
- 早期に明確なエラーで失敗させる。外部データ（API 応答・ユーザー入力・ファイル内容）を信用しない。

## 命名規約

- 変数・関数: `camelCase`（説明的な名前）
- 真偽値: `is` / `has` / `should` / `can` を接頭辞に
- 型・インターフェース・コンポーネント: `PascalCase`
- 定数: `UPPER_SNAKE_CASE`

## 避けるべきコードスメル

- **深いネスト**: 早期リターンを使う（4段を超えない）。
- **マジックナンバー**: 意味のある閾値・遅延・上限は名前付き定数にする。
- **長い関数**: 責務ごとに分割する（50行未満を目安）。

## コード品質チェックリスト

完了前に確認する:

- [ ] 読みやすく適切に命名されている
- [ ] 関数は小さい（50行未満）
- [ ] ファイルは焦点が絞られている（800行未満）
- [ ] 深いネストがない（4段以下）
- [ ] エラー処理が適切
- [ ] ハードコード値がない（定数・設定を使う）
- [ ] 破壊的変更がない（イミュータブル）

## パターン

### スケルトンプロジェクトの活用

新機能実装時は、実績あるスケルトン／テンプレートを探し、並列エージェントで評価（セキュリティ・拡張性・関連度・実装計画）し、最良のものを土台にして、その構造の中で反復する。

### 設計パターン

- **リポジトリパターン**: データアクセスを一貫したインターフェース（findAll / findById / create / update / delete）の背後に隠蔽する。ビジネスロジックは抽象インターフェースに依存させ、ストレージ実装を差し替え可能・テスト容易にする。
- **API レスポンス形式**: 一貫したエンベロープを使う（成功可否・データ本体（エラー時 null）・エラーメッセージ（成功時 null）・ページネーション用メタデータ）。
