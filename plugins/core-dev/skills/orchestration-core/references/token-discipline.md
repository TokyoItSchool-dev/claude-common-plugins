# トークン節約規律

節約はプロンプト圧縮より「呼び出し回数と読み込み量の設計」で効く。
以下は効果の大きい順に並べた常時規律である。個別スキルの手順は再実装せず参照する。

## 効果順の4規律

1. **重複 LLM 呼び出しの排除**

   パイプライン設計時に LLM 呼び出し回数を数える。同じ入力を複数回加工していないか確認する。
   例: 「抽出→要約→整形」を別々の呼び出しに分けている場合、1回のプロンプトで統合できないか検討する。
   実績: 3回加工→1回統合で約67%削減。

2. **選択的実行**

   全件検証・全件変換をやめ、必要なものだけ処理する。
   例: Vision 検証は差分のあるスライドだけ、テストは影響範囲だけ、Lint は変更ファイルだけに絞る。
   「念のため全部」は禁止。対象範囲を明示できない場合は先にスコープを特定してから実行する。

   例外: **独立した作業の並列分割は重複ではない**。「1機能＝1サブエージェント」の細粒度並列 fan-out は推奨される既定動作であり、この規律の禁止対象は同一作業の重複実行と「念のため全部」の網羅的な無駄打ちのみ。

3. **結論のみ返却**

   サブエージェントには「生のファイル内容・探索ログではなく、結論・要約・file:line を返す」よう常に指示する。
   メインのコンテキストを生データで汚染しない。委譲プロンプトに返却形式（要約か diff か一覧か）を明記する。

4. **フェーズ境界で /compact**

   調査→計画、計画→実装の境界で実行する。実装の途中ではしない。

## 定期監査

- コンテキスト逼迫を感じたら、ロード済みの MCP・エージェント・ルールを棚卸しする。
  MCP が最大レバー（1ツール≈500トークン常駐）であるため、未使用 MCP の無効化を最優先で検討する。
- 監査結果は都度記録し、次回監査との差分（増加傾向にあるコスト要因）を追う。

## コンテキストウィンドウの使い方

- 窓の最後の20%では大規模リファクタ・複数ファイル実装・複雑デバッグを開始しない。
  単一ファイル編集・ドキュメント更新等の低感度タスクに留める。
- 長大タスクはセッション分割を計画段階で織り込む。分割点はフェーズ境界（調査/計画/実装/検証）に合わせる。
- 分割前に現在の状態（決定事項・未完了項目・次の一手）をファイルに書き出し、再開コストを最小化する。
