# モデルルーティング判定表

モデル階層・タスク割り当て・effort 指定・エスカレーションの正は本書である（orchestration-core スキル全体が委譲方針の正。`CLAUDE.md`（プロジェクトまたはユーザーのもの）はメインセッションの役割のみを定める）。

原則は「最も安い十分なモデル」。コスト序列（性能序列も同じ）は Haiku < Luna < Sonnet < Opus < Fable。Luna は Codex 側モデル（ChatGPT サブスク定額）。ただしリミットが小さいためレビュー専用に限定して使う。常に Luna・effort xhigh。最重要タスクの検証は Fable へ回す。

- **難易度に迷ったら一段安いモデル**で試し、失敗したらエスカレーションする（下記「エスカレーション」）。
- **Fable サブエージェントの用途制限**: 最重要タスクの検証・レビュー・重要な設計・難解なデバッグ・計画立案に限定する（計画規模が大きい場合は計画立案に Fable を積極使用してよい）。調査・実装への Fable 使用は禁止（コスト最高のため不経済）。計画に付随する調査も Opus / Sonnet に委譲し、Fable には調査させない。メインセッション自体はモデルによらずオーケストレーションに徹する。

## effort の明示指定

サブエージェント（Haiku/Sonnet/Opus）を使うワークフローでは、タスク難易度に応じて effort を `high` / `xhigh` / `max` から明示的に指定する（`low` / `medium` は使用しない）。

- 目安: 機械的タスク＝`high`、通常の実装・探索＝`xhigh`、根本原因調査・アーキテクチャ判断・検証/judge 段＝`max`。
- Workflow ツール: `agent(prompt, {model, effort})` の `opts.effort` で指定する。省略しない。
- Agent ツール: effort パラメータが存在しないため、委譲プロンプト冒頭に期待する思考の深さを英語で明記して代替する（例: "Reason thoroughly and verify your work before concluding."）。effort パラメータが利用可能になった場合は同じ high/xhigh/max 基準を適用する。

## Step 1: 即決ルール（まずこれ。該当したらスコアリング不要）

| タスクの性質 | 割当 |
|---|---|
| 一括置換・整形・ログ収集・リンク/パス実在チェック・単純抽出・1〜2行の自明な修正 | Haiku |
| 単一ファイル修正・定型テスト追加・通常のコードベース探索・資料のMarkdown変換 | Sonnet |
| 複雑バグの根本原因調査・アーキテクチャ横断リファクタ・計画/設計ドラフト作成・特に複雑または重要なタスク（実装・調査・計画）・ライブラリ仕様の深掘り | Opus |
| Web 検索・軽量な調査 | Haiku / Sonnet + WebSearch |
| コードレビュー・計画レビュー・レビュー観点のセカンドオピニオン（Claude 系が実装/立案した成果物が対象） | Codex Luna・effort xhigh（常時。Step 3 のゲート必須） |
| 計画立案（実装計画・設計書・PRD のドラフト） | Opus / Fable（計画規模が大きい場合は Fable を積極使用）。Agent ツール `subagent_type: core-dev:planner` / `Plan` / `model: opus` / `model: fable`。計画に付随する調査は Opus / Sonnet |
| 最重要タスクの検証・重要な設計・難解なデバッグ | Fable（Codex はレビュー専用のため使わない） |
| 10件超の同型タスク | Workflow ツールでパイプライン化（各段のモデルは Sonnet / Opus） |

注: 独立したタスクは並列 fan-out が既定。「1機能＝1サブエージェント、1タスク＝1サブエージェント」の粒度で分解し、単一メッセージで同時起動する。逐次は依存関係がある場合のみ。

注: Workflow 化は同型・大量タスクのみが対象。異種の細粒度タスクは件数によらず Agent の並列 fan-out で処理する（Workflow に押し込まない）。

「メイン直接」の割当は存在しない。メインはオーケストレーション専任であり、1〜2行の自明な修正も Haiku/Sonnet へ委譲する。メインが直接行ってよいのは受入判定のための読み取り専用の証跡確認のみ。

## Step 2: 迷った時のみ4軸スコアリング

- 定型度（0=完全定型 / 1=半定型 / 2=非定型）

- 影響ファイル数（0=1個 / 1=2〜5個 / 2=6個以上）

- リスク（0=使い捨て・可逆 / 1=通常 / 2=本番・セキュリティ・データ損失可能性）

- 必要推論深度（0=機械的 / 1=通常の実装判断 / 2=設計判断 / 3=横断的アーキテクチャ判断）

合計 0〜2 → Haiku、3〜5 → Sonnet、6以上 → Opus。

下限ルール: リスク=2（本番・セキュリティ・データ損失可能性）の場合は合計値に関わらず**最低 Sonnet**。リスク=2 かつ推論深度≥2 なら Opus。

注: 合計 6 以上でかつリスク=2 または推論深度=3（特に複雑または重要）の場合は、Opus（計画規模が大きい場合は Fable も検討）に割り当てる。成果物のレビューは Step 3 の Codex ゲートに従い Codex（常に Luna・effort xhigh）へ回す。最重要タスクの検証は Fable へ回す。

## Step 3: Codex ゲート（役割判定）

Codex はレビュー専用。回してよいのはレビュー系タスクのみ:

- コードレビュー・計画レビュー（Claude 系が実装・立案した成果物が第一候補。Luna・effort xhigh が既定）

- レビュー観点のセカンドオピニオン

- 重要成果物のレビュー（本番影響・セキュリティ・データ損失リスクを伴う変更、計画書等の重要ドキュメント）。常に Luna・effort xhigh。最重要タスクの検証は Codex ではなく Fable に回す

Codex に回さない: 実装・調査・計画立案・Web 調査（Claude 系 Haiku/Sonnet/Opus、Web 調査は WebSearch で行う）、および定型・低難度の作業（コスト面で不経済。Haiku/Sonnet/Opus で足りるものは回さない）。

Codex に回す際の注意:

- ローカルファイル読取は可能な場合が多いが、下記プローブで確認する。レビュー対象のファイル I/O を伴う委譲の成果物は [CODEX-AUDIT] と裏取り3点セット（verification.md）で必ず検証する。
- 確実性を優先する場合は、レビュー対象コード・資料を委譲文にインライン貼付する方式を使う。

記録行:

Codex のローカルファイル読取可否は環境ごとに異なるため、初回に既知テキストを読ませるプローブで確認し、結果を記録する。

Codex へのレビュー依頼は小さな単位に分割する（失敗時の切り分けとリミット節約のため）。

認証は ChatGPT サブスク。`OPENAI_API_KEY` は設定しない（設定すると API 従量課金に切り替わるため厳禁）。

## Opus コストガード

背景: 実測で Opus がコスト全体の約87%を占め、単発セッションで高額な暴走が発生した事例がある。

- Opus への委譲は必ず1タスク単位に分割する。複数論点を1委譲に詰め込まない。

- 委譲前にスコープ宣言（対象ファイル上限・停止条件・返却形式）を委譲文に明記する。

- メイン自身が Opus の場合、フェーズ境界（調査→計画、計画→実装）ごとに `/compact` を必須化する。

- セッションが長引いたら、コスト実測を確認し、分割・compact を検討する。

## Haiku 活用の具体例

具体例:

- Markdown 一括整形

- frontmatter 一括修正

- リンク/パス実在チェック

- ドキュメントの見出し構成抽出

- 試験問題の解答分布集計

- ビルド/テストログの収集・要約

- ファイル一覧・行数カウント等の機械的インベントリ

## エスカレーション

- 同一タスクで2回失敗したら1段上のモデルへ引き上げる（Haiku→Sonnet→Opus→Fable）。同一モデルで3回以上リトライしない。Codex はエスカレーション先に含めない（レビュー専用）。

- Fable サブエージェントでも2回失敗した場合に限り: メインが直接介入する（最終手段中の最終手段）。

- エスカレーション時は失敗の経緯（何を試して何がだめだったか）を委譲文に含め、ゼロからやり直させない。

## フェーズ別の既定割当

- 調査・変換・整形 = Sonnet

- 計画/設計ドラフト・複雑な調査・特に複雑または重要なタスク（実装・調査・計画） = Opus（大規模な計画立案は Fable も可）

- Web調査・軽量調査 = Haiku / Sonnet + WebSearch

- コードレビュー・計画レビュー・レビュー観点のセカンドオピニオン = Codex Luna・effort xhigh（常時）

- 最重要タスクの検証・重要な設計・難解なデバッグ = Fable

- 機械的一括処理・機械的な動作確認（テスト実行・ログ収集） = Haiku

- 委譲・受入判定・最終統合 = メイン（実作業はしない）
