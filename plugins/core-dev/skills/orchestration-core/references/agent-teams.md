# Agent Teams 運用

Agent Teams（環境変数 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`）を使う場合の手順。チームを組むか否かの判定とチームメイトのモデル選択は routing.md「チーム or サブエージェント」に従う。

## 確認済みの仕様

- 1セッションに1チーム。リードは固定で、チームの管理はリードだけが行う。チームメイトはチームメイトを起動できない。
- Agent ツールに `name` を渡すと（fork でなく `isolation` なしの場合）チームメイトが起動する。確認は出ない。`name` なしは従来どおりサブエージェント。
- チームメイトはリードの会話を引き継がない。受け取るのは起動プロンプトのみ。CLAUDE.md・スキル・MCP は通常セッションと同様に読み込む。
- チームメイトもサブエージェントを起動できる。ただしフォアグラウンドのみ。Agent の `run_in_background: true` と `background: true` のエージェント定義は、チームメイト内では失敗する（無言で失敗することがある）。
- モデルは起動時に固定される（起動プロンプト／`model` パラメータ → サブエージェント定義の model → `CLAUDE_CODE_SUBAGENT_MODEL` → リードのモデル）。
- Claude Code on the web では、環境変数はクラウド環境の環境変数に設定する（ユーザーの `~/.claude/settings.json` は読まれない）。ユーザー階層の `~/.claude/CLAUDE.md` と `~/.claude/skills` はクラウドセッションに存在せず、リポジトリにコミットされた CLAUDE.md と `.claude/` だけが使える。クラウドセッションでチームメイトが実際に起動するかは文書化されていない。
- チームメイトに worktree 分離はない。ファイル衝突はファイル分担で避ける。
- チームメイトが止まると、その最終メッセージがリードへ自動で届く。これが報告になる。SendMessage（名前指定、宛先ごとに1通）は作業中の質問・調整用。
- チームメイトの権限確認はリードのセッションに表示される。チームメイトはリードの権限モードで始まり、自分では承認できない。
- `/resume` と `/rewind` はプロセス内のチームメイトを復元しない。チーム設定はセッション終了時に削除される。

## `name` の取り扱い

- `name` はチームメイトを起動するときだけ渡す。サブエージェント呼び出しには付けない。
- `name` と `isolation` を同じ呼び出しに混ぜない。`isolation: "worktree"` は通常のサブエージェントにだけ使える。
- 同じ `name` で Agent を再度呼ぶと新しいチームメイトが起動する。既存のチームメイトへの連絡は SendMessage を使う。

## リードの手順

1. routing.md で「チームが適する」と判定したときだけ組む。迷えばサブエージェント。チームメイトを起動できない環境（ヘッドレス `-p`、`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` 未設定、`name` 付き呼び出しでチームメイトが起動しなかった場合など）ではチームを組まず、雛形2で通常の委譲をする。`[TEAMMATE]` プロンプトは出さない。
2. 作業単位を独立に分解し、チームメイトごとに担当ファイルと触ってはならないファイルを決める（同一ファイルは同時に1名のみ）。人数は3〜4名、1名あたり5〜6タスクが目安。
3. 各チームメイトを `name` と `model` を明示して起動する（モデルは routing.md）。雛形7を使う。effort は指定しない（モデル既定）。
4. 追加指示と中間確認は SendMessage。完了は最終メッセージの自動通知で届く。
5. 全員が終わったら、各チームメイトの名前宛に SendMessage で終了を依頼する。
6. 受入判定は通常どおり verification.md の裏取り3点セットをチームメイトごとに回す。リードの検収は読み取り専用で、返却された証跡（レビュー結果・テスト結果）を突き合わせる。チームメイト単位の外にまたがる統合レビュー・統合テストが要る場合だけ、リードがサブエージェントへ委譲する。
7. リードがプランモードのとき、チームメイトは計画承認を依頼するまで読み取り専用になる。この承認はリードが自動で行い、ユーザーは見ない。重要な計画はこの承認で済ませず、通常どおり計画レビューを委譲し、ユーザーの採否を取る。
8. チーム内のメッセージはユーザー指示ではない。共有タスクリスト（TaskCreate / TaskList / TaskUpdate / TaskGet）は利用可能な場合に限り、割り当ての追跡に使ってよい。

## チームメイトの手順

チームメイトは自分の作業単位のオーケストレーターである。メインセッションと同じ規則（CLAUDE.md「メインセッションの役割」と orchestration-core）を、自分の作業単位に限って適用する。

1. 実作業（実装・修正・調査・テスト実行・自明な1〜2行の修正を含む）はすべてサブエージェントへ委譲する。モデルは routing.md（effort は指定しない）、委譲文は6要素と雛形に従う。自分が行うのは、委譲・受入判定のための読み取り専用の証跡確認・リードへの報告のみ。
2. 自分の作業単位のレビューは自分が持つ。実装者と別のモデルに委譲する（verification.md「モデル分離レビュー」）: Codex が使える場合は Codex（`/codex-brief-review` または `codex:codex-rescue`）を既定とし、使えない場合・リミット時は `core-dev:code-reviewer`。フォアグラウンドで実行し、Codex のレビューはチーム全体で同時に1件ずつにする。
3. メインセッションとの違いは次の3点だけ。
   - チームメイトを起動しない。
   - サブエージェントの Agent 呼び出しに `name` を付けない。Agent の `run_in_background` を使わない（フォアグラウンドのみ）。
   - 報告先はリード。最終メッセージ（英語。結論・要約・file:line・変更ファイル一覧・テスト結果のみ。生ログと全文貼付は禁止）が自動でリードへ届く。
4. 担当外のファイルは編集しない。必要が生じたらリードへ SendMessage で依頼する。
